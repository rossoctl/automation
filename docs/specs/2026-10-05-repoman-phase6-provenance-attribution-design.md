**Date:** 2026-10-05
**Status:** Approved (2026-10-05)

**Companion (agent-skills):** [#37](https://github.com/rossoctl/agent-skills/issues/37) (`report.py` multi-owner)
**Parent spec:** `docs/specs/2026-08-27-repoman-architecture.md` (§Skill layer, §State and persistence)

## Summary

Make RepoMan the single attribution anchor for every program, and close out the
consumers that Phase 1 left broken. The phase has two major sections, delivered
together as one phase (expected to land as two coordinated PRs):

- **6a — Skill provenance and attribution voice.** A per-skill `_meta.json`
  carrying a pinned commit SHA, written lazily by each skill's own entry point,
  is consumed to stamp `Generated by RepoMan <skill>@<sha>` plus a canonical
  `rossoctl/agent-skills` `blob/<sha>` link into the PR and issue bodies the
  live programs create. Every platform-leaking `OpenClaw` / `Rossoctl`
  attribution string across all program scripts is standardized to a neutral
  RepoMan voice.
- **6b — Close #86.** Port the three deferred consumers
  (`pr-review-scanner.sh`, `pr-review-impact.sh`, `weekly-report.sh`) off the
  single-global-`$ORG` API deleted in Phase 1 onto `repoman_config` /
  `repoman_get_repos`; coordinate the `report.py` owner/name change
  (agent-skills #37); and re-enable their CI tests plus the dashboard
  cross-program-join guard #86 owes.

## Non-goals

- **No `_index.json` change.** The dashboard is the only reader of `_index.json`
  and it never reads `skill` / `version`; adding those fields now would be
  write-only data no code consumes. `scripts/repoman-index.sh` and the dashboard
  discovery path are untouched. Index enrichment is deferred to whatever phase
  first reads it (a future orchestrator or a dashboard provenance column).
- **No dashboard-footer SHA.** The dashboard is a report *consumer*, not a
  skill; it has no `_meta.json`. Its footer stays on the existing `blob/main`
  link.
- **No `repoman run` orchestrator** (deferred to the epic).
- **Existing `$SOURCE_REPO` attribution stays** as the fallback. The change is
  additive and never makes a working scan depend on a reachable GitHub API.

## Section 6a — Skill provenance and attribution voice

### `_meta.json` (new, one per skill, written beside the skill)

```json
{ "version": "85449be", "source": "rossoctl/agent-skills", "installed_at": "2026-10-05" }
```

**Alternatives considered for who writes it:**

1. **Standalone `repoman-skill-init.sh` bootstrap** run once at install, writing
   `_meta.json` for every skill. *Rejected:* it must know every skill a-priori,
   so adding a skill means editing a central list — the drift the stateless-skill
   model exists to avoid.
2. **Lazy, in each skill's entry point (chosen).** Each scanner/fixer, on
   startup, writes its own `_meta.json` if absent. A new skill carries its own
   provenance logic; nothing central needs updating. This is issue #77's stated
   preference.

**Behavior of the lazy writer:**

- **Create-only, write-only-on-success (self-healing).** On first run the helper
  resolves the SHA via
  `gh api repos/rossoctl/agent-skills/commits?path=skills/<name> --jq '.[0].sha'`.
  On success it writes `_meta.json`; on failure (offline, unauthenticated, rate
  limited) it writes **nothing**, logs a warning, and the run falls back to the
  existing `blob/main $SOURCE_REPO` attribution. Because the file stays absent,
  the next run retries and self-heals once the API is reachable. It must
  **never** write a sentinel such as `{"version":"unknown"}` — a present file
  would stop the retry and pin the skill to a bogus version forever.
- The entry point **only creates a missing** `_meta.json`; it never overwrites
  an existing one. Refreshing on skill update is the deploy layer's job
  (OpenClaw's repo-sync rewrites it on pull and prompts the user; DAM rewrites
  it at install), per the architecture spec's §Skill layer.
- The skill directory is derived from the caller's own location
  (`SCRIPT_DIR` via `BASH_SOURCE`), not hardcoded, so it resolves on both DAM
  (`~/skills/<name>/`) and OpenClaw (`~/agent-skills/skills/<name>/`).
- Provenance resolution never affects the scan/fix exit code.

### Shared helpers in `github-api.sh`

Two functions, implemented in `github-api.sh` (which `program-lib.sh` sources,
so every entry point that sources `program-lib.sh` picks them up). They live
alongside the other GitHub-API helpers, are tracked by the
`test-lib-inventory.sh` function-surface guard, and the agent-skills copy syncs
byte-identically under the dashboard parity contract:

- `resolve_skill_meta <skill-dir> <skill-name>` — the create-only lazy writer
  above; echoes the resolved SHA, or empty on failure.
- `skill_attribution <skill-name>` — returns the attribution block: the
  pinned-SHA RepoMan footer on success, the `blob/main $SOURCE_REPO` fallback
  otherwise.

### Attribution rewrite

**(A) Linked provenance footer → pinned-SHA RepoMan footer.** Applied to the two
live programs (link-health, dep-bump) only. Each falls back to the current
`blob/main $SOURCE_REPO` form when the SHA cannot be resolved. Target in every
row is `Generated by RepoMan <skill>@<sha>` followed by the agent-skills
`blob/<sha>` SKILL.md link
(`https://github.com/rossoctl/agent-skills/blob/<sha>/skills/<skill>/SKILL.md`).

| Script:line | Current | Target |
|---|---|---|
| `link-health-scanner.sh:541` | `Generated by the [Rossoctl Link Health Scanner](…/blob/main/standing-orders/link-health.md)` | `Generated by RepoMan link-health-scanner@<sha>` + agent-skills `blob/<sha>` link |
| `link-health-fixer.sh:532` | `Generated by the [Rossoctl Link Health Fixer](…/blob/main/…)` | `Generated by RepoMan link-health-fixer@<sha>` + agent-skills `blob/<sha>` link |
| `dep-bump-scanner.sh` | *(no footer today)* | **ADD** `Generated by RepoMan dep-bump-scanner@<sha>` + agent-skills `blob/<sha>` link |
| `dep-bump-fixer.sh:75` | `FIXER_SIGNATURE="Automated analysis by Rossoctl Dep Bump Fixer"` | `Generated by RepoMan dep-bump-fixer@<sha>` + agent-skills `blob/<sha>` link |

**(B) Inline platform-leak markers → neutral RepoMan voice.** String-only; safe
on every program script including pr-review (whose code 6b makes runnable). The
AI-tell colon is dropped (`Detected by:` → `Detected by`).

| Script:line | Current | Target |
|---|---|---|
| `link-health-scanner.sh:256` | `Detected by: OpenClaw Link Health Scanner (cron: …)` | `Detected by RepoMan Link Health Scanner` |
| `link-health-scanner.sh:479` | `*Generated by OpenClaw Link Health Scanner. Do not edit manually.*` | `*Generated by RepoMan Link Health Scanner. Do not edit manually.*` |
| `link-health-fixer.sh:453,501,513,651` | `… OpenClaw Link Health Fixer …` (×4) | `… RepoMan Link Health Fixer …` |
| `dep-bump-scanner.sh:480` | `Detected by: OpenClaw Dep Bump Scanner (scan …)` | `Detected by RepoMan Dep Bump Scanner (scan …)` |
| `pr-review-scanner.sh`, `pr-review-fixer.sh` | `OpenClaw`-style strings | `RepoMan` voice (strings only; the pinned-SHA footer is deferred until the 6b port makes this code run) |

Note that `link-health-scanner.sh:256` (the per-finding **issue** body) and
`:541` (the body of the **report-publishing PR** opened against
`$REPORT_TARGET_REPO`) are different artifacts rendered in different places and
never shown together — which is how the two voices drifted apart.

**Explicitly untouched:** the `<!-- reviewed: SHA -->` marker (that SHA is the
reviewed PR commit, not a skill version), and the dashboard footer.

### 6a tests

A new `tests/test-skill-meta.sh` stubs `gh` on `PATH` and covers all branches:

1. `gh` succeeds → `_meta.json` is written and the `@<sha>` link is emitted;
2. `gh` fails → nothing is written and the `blob/main` fallback is emitted;
3. a pre-existing `_meta.json` is read, never overwritten, and no `gh` call is
   made.

Wire the suite into both the `Run test suite` list and the "repoman tests"
shellcheck group in `.github/workflows/tests.yml` (the workflow uses explicit
lists, not globs; an unlisted test silently never runs).

## Section 6b — close #86 (deferred consumer port)

### Port off the deleted single-`$ORG` API

Phase 1 removed `load_org_profile` / `get_core_repos` from `scripts/org.sh` in
favor of `repoman_config` + `repoman_get_repos` (owner/name tuples from
`~/.repoman/repos.json`). Three consumers still call the deleted API and abort
at exit 127. Apply the same migration Phase 1 already proved on the link-health
and dep-bump scanners:

- **`pr-review-scanner.sh`** (`:65` `load_org_profile`, `:77` `get_core_repos`)
  → `repoman_config` + `repoman_get_repos`; drop the `--org` flag and its usage
  text.
- **`pr-review-impact.sh`** (`:99`, `:41`) → the same migration.
- **`pr-review-fixer.sh`** — already clean of the deleted symbols; verify it
  end-to-end against the ported scanner.
- **`weekly-report.sh`** (`:67`, `:70`) → the same migration; its `--org`
  passthrough to `report.py` is resolved by the agent-skills change below.

### agent-skills #37 — `report.py` carries `{owner, name}` (separate lockstep PR)

`skills/github-weekly-report/scripts/report.py` assumes a single global org and
rebuilds every slug as `f'{org}/{name}'` (`:64`–`:77`); its
`normalize_repo_args()` (`:33`–`:60`) rejects cross-owner entries and strips the
owner. Per #37: remove the cross-owner rejection and carry `{owner, name}` as a
pair through the report data model, so one report can span repos from multiple
owners. This is a Python change in agent-skills, its own PR, landing alongside
6b.

### 6b tests

- Re-add to `.github/workflows/tests.yml` (run list and shellcheck group):
